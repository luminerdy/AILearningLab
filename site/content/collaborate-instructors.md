# Teaching COLLABORATE

Students improve a bounded project and teaching lab through evidence, comparison, focused changes, and trials. The outcome is **I can collaborate with AI to make a checked improvement and explain why it helped.**

## Prepare and support different starting points

Prepare Pi 500/Codex CLI workstations for students entering directly and returning students. ASK completion is not required. Students can bring a small working project or use a tested starter with run instructions. An existing teaching lab is not required; students create or revise one in Lab 3. Recheck access before class. Software-only projects are a complete path; optional hardware needs the existing instructor setup and review. Follow [official Codex CLI documentation](https://learn.chatgpt.com/docs/codex/cli) for setup and permissions.

Offer the same core activities to everyone, with optional stretch tasks. Help a first-time learner narrow an observation and perform a check. Invite experienced learners to investigate alternatives, add a meaningful automated check, or adapt their lab for another audience. Avoid assigning ranks or requiring extra features to demonstrate learning.

Projects should have one learning goal, one bounded change at a time, and three observable checks. Redirect a large commercial or multiplayer game idea toward one mechanic that can be tested and taught today. Good boundaries include three quiz questions, two story choices, one simulation control, or one page with one interaction. Hardware naturally narrows scope, but is not required.

Use individual work with open room discussion. Peer trials are optional; each student keeps their own evidence. Record baseline checkpoints and demonstrate restoration. Ensure a student understands a command or hardware action before authorizing it.

## Prepare a direct-entry starter

Supply a small tested project, such as a three-question quiz or two-choice story. Include code, exact run steps, expected outcomes, and a short explanation. Verify it on the classroom image before use. Choose a visible improvement opportunity, such as clearer feedback. Provide a brief terminal and checkpoint orientation for newcomers. Starter code and hardware setup must be prepared and tested before teaching; this curriculum does not bundle a tested starter program.

## Proposed schedule

Two two-hour sessions are a first pilot estimate, not measured completion times. Build in extra sessions when needed.

| Session | Minutes | Focus |
|---|---|---|
| 1 | 0–15 | Reopen projects, save baseline, demonstrate evidence-based feedback |
| | 15–65 | Lab 1: trial, observation, scope, compare options |
| | 65–75 | Break |
| | 75–110 | Lab 2: implement focused change and begin checks |
| | 110–120 | Save versions, findings, and next question |
| 2 | 0–10 | Reopen and recap |
| | 10–40 | Finish Lab 2 checks, investigation, decision |
| | 40–65 | Lab 3: revise teaching instructions |
| | 65–75 | Break |
| | 75–110 | Trial, revision, and recheck |
| | 110–120 | Demonstration and reflection |

Students working independently can use the per-lab estimates in the [workbook](collaborate-workbook.md). Schedule optional stretches separately when needed.

## Demonstrate collaboration

Use a small tested project. Show one observation, such as a quiz giving confusing feedback after an incorrect answer. Ask AI for two small approaches before edits. Compare them against the learner's goal, choose one, predict the result, and request a focused change. Inspect changed files, run normal and unusual cases, and check preserved behavior. If no failure occurs, explain the evidence for keeping the change. Do not depend on a live AI mistake.

Model useful feedback: “When I entered this value, I expected this response, but observed this message.” Model disagreement too: “That adds more scope than we need. Can we solve it with a smaller change?”

## Coaching prompts

- What observation makes this improvement worth doing?
- Which assumption could you check before editing?
- Why did you choose this approach over the alternative?
- What behavior must still work afterward?
- What evidence would make you keep or revert the change?
- What should the next learner understand?

Watch for broad rewrites, accepting an AI explanation as proof, tests that miss the criteria, and instructions that no longer match code. Ask for one focused next action. Do not force revisions when the checks support keeping a result.

## Evidence of learning

| Practice | Evidence |
|---|---|
| Notice | Reproducible observation and saved baseline |
| Discuss | Useful question, alternatives, and reasoned choice |
| Direct | One scoped request and inspected changes |
| Check | Expected/actual results, including preserved behavior |
| Adjust | Finding-linked correction, or evidence-based keep/revert decision |
| Teach | Updated lab, labeled trial, and checked explanation |

Assess the process as well as the artifact. Confidence should be grounded in something the student can now investigate or explain. If unfinished, record what is established and arrange continuation.

## Improve the next run

Record scope creep, questions that helped, checks students performed independently, trial confusion, and actual time. Revise from those observations. Offer ORIENT as another starting choice when students would benefit from capturing project context and continuing in a fresh AI session; that curriculum is a future addition.
